# MTTR vs MTBF

MTTR and MTBF look like a neat pair, but they are answering different questions. [IBM's overview](https://www.ibm.com/think/topics/mttr-vs-mtbf) has the clean version: MTBF is total operating time divided by number of failures, so it tells you how long a repairable system tends to run before it breaks again. MTTR is total downtime divided by number of failures, so it tells you how long the breakage tends to last. One is about the distance between failures. The other is about the speed of recovery. Put less politely: MTBF tells you how often the pain shows up, MTTR tells you how long you have to sit with it.

That distinction matters more than the formulas make it seem. In a factory, MTBF is useful because machines age, parts wear out, spares need to be stocked, and maintenance schedules need some statistical basis. In software, MTBF is a more slippery metric. Failures are not always independent, the system changes underneath you every deploy, and "failure" can mean anything from one customer seeing errors for two minutes to the whole product being unavailable for an afternoon. [Atlassian notes](https://www.atlassian.com/incident-management/kpis/common-metrics) that MTBF and MTTR can be combined into availability with `MTBF / (MTBF + MTTR)`, which is mathematically tidy, but it can also hide the thing users actually felt. Ten tiny outages and one brutal outage can produce a calm-looking average.

MTTR has its own trap: nobody agrees what the R stands for. It can mean repair, recovery, respond, restore, or resolve, and those are not the same clock. Repair might start when an engineer begins fixing the broken part. Recovery might run from user impact to service restoration. Resolve might include the follow-up work that prevents the same incident coming back next week. [PagerDuty](https://www.pagerduty.com/resources/devops/learn/what-is-mttr/) and Atlassian both make this point, and it is not pedantry. A team can improve "mean time to respond" by paging faster while making no progress on diagnosis. It can improve "mean time to repair" while still leaving users in the dark. If you do not define the clock, the number becomes a status-report decoration.

The practical lesson is that MTBF belongs to planning and design, while MTTR belongs to operating the system you actually have. Raise MTBF with simpler architecture, fewer risky changes, better testing, redundancy, and maintenance. Lower MTTR with better alerts, rollback paths, runbooks, access, incident roles, and postmortems that feed real work back into the backlog. Google SRE is useful here because it treats outages as inevitable in complex systems and pushes teams toward fast mitigation, playbooks, automation, and learning; it also warns in its [incident metrics report](https://sre.google/resources/practices-and-processes/incident-metrics-in-sre/) that mean-based incident metrics can be poor tools for trend analysis. So use MTBF and MTTR, but do not worship them. The real question is simpler: are users hit less often, for less time, and is the system learning every time it fails?
